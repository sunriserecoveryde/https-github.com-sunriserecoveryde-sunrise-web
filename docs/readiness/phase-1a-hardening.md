## 2. Versioned Migrations

### Migration file
`lib/db/drizzle/0000_perpetual_rafael_vega.sql`

Generated by `drizzle-kit generate`. Applies all DDL from an empty database.

### Key ordering fix
The original generated SQL placed `CREATE UNIQUE INDEX` statements **after** `ALTER TABLE ADD CONSTRAINT … FOREIGN KEY` statements for composite foreign keys. PostgreSQL requires a unique constraint or unique index on the referenced column tuple before the FK can be added — so the migration failed on a clean database.

**Fix:** The three composite-FK prerequisite indexes are now created before the FK constraints:

```
-- Before FK constraints:
CREATE UNIQUE INDEX "idx_sos_facilities_org_id_id"  ON sos_facilities  (org_id, id);
CREATE UNIQUE INDEX "idx_sos_patients_org_id_id"    ON sos_patients    (org_id, id);
CREATE UNIQUE INDEX "idx_sos_user_refs_org_id_id"   ON sos_user_identity_refs (org_id, id);

-- Then FK constraints (can now find their referenced indexes):
ALTER TABLE sos_patients ADD CONSTRAINT fk_sos_patients_org_facility   …
ALTER TABLE sos_episodes_of_care ADD CONSTRAINT fk_sos_episodes_org_patient …
ALTER TABLE sos_episodes_of_care ADD CONSTRAINT fk_sos_episodes_org_facility …
ALTER TABLE sos_staff_profiles ADD CONSTRAINT fk_sos_staff_profiles_org_user …
```

### Migration tracking
`drizzle.__drizzle_migrations` table is created by `drizzle-kit migrate`. Migration is registered with hash `d469974922cc3fc74bbd81e20697f39d9732ae09456fc01871f6c210e4138c1c`.

### Idempotency
Running `drizzle-kit migrate` a second time reports `migrations applied successfully` with no pending migrations.

## 3. Database Schema Integrity

### Date column types
All date columns use PostgreSQL `date` type (not `text`):

| Table | Column |
|---|---|
| `sos_patients` | `date_of_birth` |
| `sos_episodes_of_care` | `admission_date` |
| `sos_episodes_of_care` | `discharge_date` |

### CHECK constraints

| Constraint | Table | Values |
|---|---|---|
| `ck_sos_organizations_status` | `sos_organizations` | `'active','inactive','suspended'` |
| `ck_sos_facilities_status` | `sos_facilities` | `'active','inactive','closed'` |
| `ck_sos_user_refs_status` | `sos_user_identity_refs` | `'active','inactive','revoked'` |
| `ck_sos_staff_profiles_status` | `sos_staff_profiles` | `'active','inactive','terminated'` |
| `ck_sos_patients_status` | `sos_patients` | `'active','inactive','discharged','transferred'` |
| `ck_sos_episodes_status` | `sos_episodes_of_care` | `'active','discharged','transferred','completed','void'` |
| `ck_sos_episodes_date_order` | `sos_episodes_of_care` | `discharge_date IS NULL OR admission_date IS NULL OR discharge_date >= admission_date` |

### Composite foreign keys (cross-tenant isolation)

These FKs prevent one organisation's data from referencing another organisation's rows.

| Constraint | Table | References | Enforcement |
|---|---|---|---|
| `fk_sos_patients_org_facility` | `sos_patients(org_id, facility_id)` | `sos_facilities(org_id, id)` | patient.org_id must match facility.org_id |
| `fk_sos_episodes_org_patient` | `sos_episodes_of_care(org_id, patient_id)` | `sos_patients(org_id, id)` | episode.org_id must match patient.org_id |
| `fk_sos_episodes_org_facility` | `sos_episodes_of_care(org_id, facility_id)` | `sos_facilities(org_id, id)` | episode.org_id must match facility.org_id |
| `fk_sos_staff_profiles_org_user` | `sos_staff_profiles(org_id, user_id)` | `sos_user_identity_refs(org_id, id)` | staff.org_id must match user identity org_id |

### Unique indexes

| Index | Table | Columns | Notes |
|---|---|---|---|
| `idx_sos_patients_org_mrn` | `sos_patients` | `(org_id, mrn)` | Prevents duplicate MRN within an org |
| `idx_sos_user_refs_org_ext_auth_ref` | `sos_user_identity_refs` | `(org_id, ext_auth_ref)` | Partial index: `WHERE ext_auth_ref IS NOT NULL` |
| `idx_sos_facilities_org_id_id` | `sos_facilities` | `(org_id, id)` | FK target for composite FKs |
| `idx_sos_patients_org_id_id` | `sos_patients` | `(org_id, id)` | FK target for composite FKs |
| `idx_sos_user_refs_org_id_id` | `sos_user_identity_refs` | `(org_id, id)` | FK target for composite FKs |

## 4. Data Mode (Fail-Closed)

### File
`artifacts/sunrise-os/src/lib/dataMode.ts`

### Truth table

| `nodeEnv` | `VITE_SUNRISE_DATA_MODE` | Result |
|---|---|---|
| `development` | `demo` | ✅ demo mode |
| `development` | `production` | ✅ production mode |
| `development` | `undefined` / `""` | ✅ demo mode (safe default) |
| `development` | any other value | ❌ `DATA_MODE_ERROR` — blocks app |
| `test` | `demo` | ✅ demo mode |
| `test` | `production` | ✅ production mode |
| `test` | `undefined` / `""` | ✅ demo mode (safe default) |
| `production` | `production` | ✅ production mode |
| `production` | `demo` | ❌ `DATA_MODE_ERROR` — **demo must never activate with real patients** |
| `production` | `undefined` / `""` | ❌ `DATA_MODE_ERROR` — must be explicitly configured |
| `production` | any other value | ❌ `DATA_MODE_ERROR` — blocks app |

### Blocking UI
When `DATA_MODE_ERROR` is non-null, both `PatientList.tsx` and `PatientDetail.tsx` display a full-page blocking error screen instead of any patient data. No mock or server data is shown.

### Production never falls back to mock
In production mode, if the API call fails, the app shows a safe error state — it does not silently render mock patients.

## 5. Authentication Boundary

### Files
- `artifacts/api-server/src/middlewares/requireIdentity.ts`
- `artifacts/api-server/src/middlewares/devIdentity.ts`
- `artifacts/api-server/src/app.ts`

### Design

```
                   +------------------+
  request          |                  |
  ────────────────>│ devIdentityMiddleware │ ← Registered ONLY when NODE_ENV !== "production"
                   │  Reads X-Dev-*   │   In production: this middleware is NOT mounted.
                   │  headers or uses │   Dev headers are silently ignored.
                   │  seed defaults   │
                   +------------------+
                          │
                          ▼
                   +------------------+
                   │ requireIdentity  │ ← Always registered for /api/v1
                   │                  │   In dev: req.devIdentity is set → next()
                   │ if (!devIdentity) │   In prod: req.devIdentity never set → 401
                   │   return 401     │
                   +------------------+
```

### Verified production behavior (NODE_ENV=production, built binary)

| Test | Result |
|---|---|
| `GET /health/live` | 200 |
| `GET /health/ready` with working DB | 200 `{"status":"ok","database":"connected"}` |
| `GET /api/v1/patients` no identity | 401 `{"error":"Authentication required"}` |
| `GET /api/v1/patients` with `X-Dev-Org-Id` header | 401 (header ignored in production) |
| `GET /api/v1/patients` with `X-Dev-Facility-Id` header | 401 (header ignored in production) |
| `GET /api/v1/patients/:id` no identity | 401 (middleware order preserved) |
| `GET /health/ready` with broken DB | 503 `{"status":"not_ready","database":"unavailable"}` |
| 401 body content | No stack traces, connection strings, or secrets |

## 7. Browser Storage Privacy

### localStorage

| Key pattern | Contents | Production behaviour |
|---|---|---|
| `sunrise_demo_session_v1` | Opaque session token (e.g. `"s8"`) | Only used in demo mode; key includes `_demo_` |
| `sunrise_sidebar_prefs_v2_<staffId>` | `{ id, pinnedPatientIds[], recentPatientIds[], favoriteModuleKeys[] }` | **`displayName` and `program` are stripped before write** |
| `sunrise-os:ua-workflow-items` | UA Drug Testing workflow state | **Write is gated on `DATA_MODE === 'demo'`; not written in production mode** |

**No patient names, MRNs, diagnoses, insurance data, clinical notes, or medication data are stored in localStorage.**

### sessionStorage
Not used for patient data.

### IndexedDB

| Database | Purpose | PHI classification |
|---|---|---|
| `sunrise-recordings` | Audio blobs for voice dictation | Keyed by session UUID (not patient UUID). Contains raw audio only — no structured PHI fields. **Caller must invoke `deleteRecording()` after processing.** |

### Version bump
`useSidebarPrefs` key was bumped from `v1` to `v2` to prevent loading stale production display names from any pre-hardening localStorage entries.

## 10. Known Limitations

1. **Phase 2 authentication not implemented.** All `/api/v1/*` requests return 401 in production until real JWT/session tokens are wired in Phase 2.

2. **Production mode patient-list screenshots require API access.** The Playwright screenshots for production mode use mocked API responses because the running dev server does not proxy `/api/v1/*` to the local api-server port without the Replit artifact router.

3. **UA Drug Testing page is demo-only.** It uses `MOCK_PATIENTS` and its localStorage write is gated on `DATA_MODE === 'demo'`. This page should be excluded or hidden in production deployments until it is backed by the real API.
