## 5. Apply these product decisions

Use the following approved defaults for the Clinical Documentation Foundation scope.

### Decision 1 — Note types

The initial allowlist is limited to:

* `progress_note`
* `nursing_note`

Do not couple note types directly to billing codes.

No billing claim or service-code generation is included.

Design the allowlist so future note types can be added through reviewed code and migrations.

---

### Decision 2 — Draft ownership

A draft note may be edited only by its original author.

Supervisors and administrators may view drafts when their scoped permissions authorize access, but they may not silently edit another author’s draft.

No draft reassignment is included.

---

### Decision 3 — Signing

Signing requires:

* A currently authenticated session
* Valid CSRF protection
* Permission to sign the note
* Continued authorization for the organization, facility, patient, and episode
* Confirmation that the user is the note author
* Current note version matching the submitted version

Do not add MFA in this phase.

Do not claim that signing without MFA satisfies every regulatory or organizational signature policy.

Record:

* Signer identity
* Signature timestamp
* Final version
* Organization
* Facility
* Patient
* Episode where applicable

---

### Decision 4 — Signed-note immutability

A signed note is immutable.

After signature:

* Text cannot be edited
* Author cannot change
* Patient cannot change
* Episode cannot change
* Facility cannot change
* Note type cannot change
* Signed timestamp cannot change

Do not implement amendments, late entries, addenda, corrections, or co-signatures in this phase.

---

### Decision 5 — Void behavior

A signed note may be voided only by a separately authorized supervisor or administrator.

Voiding requires:

* `clinical_note.void`
* Scoped patient access
* A required reason
* Audit event
* Voiding user
* Void timestamp

Voiding must not delete or overwrite the original note.

The original content must remain available to appropriately authorized audit and supervisory users.

The original author may not void their own signed note unless they independently possess the approved supervisory permission.

---

### Decision 6 — Storage and encryption posture

Clinical-note content may use the existing PostgreSQL storage architecture for this implementation phase.

Do not claim field-level encryption exists when it does not.

Document clearly:

* Clinical-note content contains sensitive health information
* Database access must be restricted
* Transport encryption is required
* Backups must be protected
* Production key-management and field-level encryption remain a separate security decision
* The implementation is not, by itself, a declaration of HIPAA or regulatory compliance

Do not put real patient information in:

* Tests
* Seeds
* Screenshots
* Logs
* Review archives

# Part 3 — Finalize the Approved Scope

## 6. Approved in-scope workflow

Implement one coherent workflow:

1. Authorized staff opens an authorized patient.
2. Staff opens the Progress Notes area.
3. Staff creates a draft note.
4. Server validates organization, facility, patient, episode, assignment, and permission scope.
5. Staff saves the draft.
6. Staff views the draft in a note timeline.
7. Original author edits the draft.
8. Optimistic concurrency prevents silent overwrites.
9. Original author signs the note.
10. Signed note becomes immutable.
11. Authorized staff can view the signed note.
12. Authorized supervisor may void the signed note with a reason.
13. Every sensitive action is audited.

---

## 7. Approved database scope

Add one primary table:

`sos_clinical_notes`

At minimum include:

* `id`
* `organization_id`
* `facility_id`
* `patient_id`
* `episode_id`, nullable only when explicitly permitted
* `author_user_id`
* `note_type`
* `status`
* `content`
* `version`
* `created_at`
* `updated_at`
* `signed_at`
* `signed_by_user_id`
* `voided_at`
* `voided_by_user_id`
* `void_reason`

Use explicit status values such as:

* `draft`
* `signed`
* `voided`

Required database protections:

* Organization consistency
* Facility consistency
* Patient consistency
* Episode consistency
* Valid note-type check
* Valid status check
* Version greater than zero
* Signed fields required when status is signed
* Void fields required when status is voided
* Signed content protected from mutation
* Appropriate foreign keys
* Appropriate indexes
* No hard delete through normal application credentials

Use database-level protection for signed-note immutability where practical.

Do not rely only on frontend controls.

---

## 8. Approved permissions

Create narrowly scoped permissions:

* `clinical_note.create`
* `clinical_note.view`
* `clinical_note.edit_own_draft`
* `clinical_note.sign_own`
* `clinical_note.void`
* `clinical_note.audit_view`

Do not authorize note operations from a generic patient-chart permission alone.

Every operation must also require valid patient access through the scoped-grant model.

---

## 9. Approved API scope

Implement only the reviewed equivalents of:

```text
POST   /api/v1/patients/:patientId/clinical-notes
GET    /api/v1/patients/:patientId/clinical-notes
GET    /api/v1/patients/:patientId/clinical-notes/:noteId
PATCH  /api/v1/patients/:patientId/clinical-notes/:noteId
POST   /api/v1/patients/:patientId/clinical-notes/:noteId/sign
POST   /api/v1/patients/:patientId/clinical-notes/:noteId/void
```

Every route must enforce:

* Authenticated session
* CSRF for state changes
* Organization scope
* Facility scope
* Patient scope
* Exact patient-assignment binding where applicable
* Note-specific permission
* Ownership for draft edits and signing
* Current version for modifications
* Minimum-necessary response fields
* Audit requirements

Do not accept organization, facility, author, signer, or status authority directly from the client.

Derive authoritative identity and scope from the server session and database.

## 14. Repository and service requirements

Create dedicated clinical-note repository and service layers.

Do not put all note logic directly in route handlers.

The service must enforce:

* Patient authorization
* Permission checks
* Draft ownership
* Status transitions
* Version checking
* Signing rules
* Void rules
* Minimum-necessary projections
* Transactional audit events

Use transactions for:

* Create plus audit
* Edit plus audit
* Sign plus audit
* Void plus audit

No state-changing operation may report success when its required audit record fails.

---

## 15. Concurrency requirements

Use optimistic concurrency.

Every draft update must submit the expected version.

When the stored version differs:

* Return HTTP 409
* Do not overwrite newer content
* Return a safe conflict response
* Let the frontend preserve the user’s unsaved text
* Provide reload/retry behavior

Signing must also verify the expected current version.
