## Current problem

The Clinical Documentation Review currently determines field destinations using `inferFieldId()` and regular-expression matching against finding titles or explanation text.

Examples include looking for words such as:

* intervention
* response
* treatment goal
* safety
* risk
* follow-up
* level of care

Although the current fallback prevents broken navigation, this approach is fragile.

A wording change such as:

* “Document what the clinician did”
* “Describe how the patient reacted”
* “Clarify next-session planning”

could stop navigation from working even though the underlying finding still refers to a known field.

## Objective

Assign field destinations as structured metadata when findings are created.

Do not infer navigation destinations later by parsing user-facing finding text.

Each finding generator should explicitly provide:

* `targetFieldId`, when a valid form destination exists
* `fallbackTool`, when only detailed AI review is available
* `recommendedAction`
* `sourceFields`

The rendered title and explanation may change without breaking navigation.

# 1. Remove Text-Based Field Inference

Remove or retire `inferFieldId()` from the normal finding-generation path.

Do not use regular expressions against:

* Finding titles
* Finding explanations
* Recommended-action text
* Missing-element labels
* User-facing AI output

to determine field navigation.

A text-based inference helper may remain only as a temporary compatibility fallback for legacy findings, if necessary.

If retained:

* Clearly mark it as deprecated.
* Do not use it for newly generated Clinical Documentation Review findings.
* Document exactly which legacy result still requires it.

Preferred result:

No active review finding depends on text parsing for its destination.

The renderer should not need to interpret the title to know where to navigate.

# 4. Map Findings at Their Source

Assign destinations where the review results are converted into consolidated findings.

Use mappings such as:

## Clarity findings

A clarity issue should target the specific section where the issue occurred.

Examples:

* Behavior wording issue → `behavior`
* Intervention wording issue → `intervention`
* Patient Response wording issue → `response`
* Plan wording issue → `plan`
* SOAP Subjective issue → `subjective`
* SOAP Objective issue → `objective`
* Assessment wording issue → `assessment`
* GIRP Goal wording issue → `goal`

If the existing clarity result does not identify its source section, update its internal result metadata to include the section identifier.

Do not parse the displayed revised text to determine the section.

## Medical-necessity findings

Use explicit mappings:

* Intervention missing → `intervention`
* Patient response missing → `response`
* Follow-up planning missing → `plan`
* Continued-service rationale missing → `plan`
* Level-of-care support missing → `plan` unless a dedicated field currently exists
* Treatment-goal connection missing → `goal` when GIRP is active
* Safety statement missing → `assessment` when DAP or SOAP is active
* Required patient missing → `patientSelect`
* Required note type missing → `noteTypeSelect`

When the current note format lacks the ideal field:

* Select the safest relevant existing field, or
* Omit `targetFieldId` and provide `fallbackTool`

Do not point to a field that does not exist in the current format.

## Consistency findings

Structured consistency results should explicitly identify both source fields where possible.

Example:

```ts
{
  sourceFields: ["Assessment", "Structured craving score"],
  targetFieldId: "assessment"
}
```

If two editable note fields conflict, select the field most likely to require clinician clarification.

Do not automatically change either field.

## Completeness findings

Completeness checks should be mapped from their underlying requirement definitions.

Create a configuration map such as:

```ts
const DOCUMENTATION_REQUIREMENTS = {
  intervention: {
    targetFieldId: "intervention",
    priority: "important"
  },
  response: {
    targetFieldId: "response",
    priority: "important"
  },
  plan: {
    targetFieldId: "plan",
    priority: "important"
  }
};
```

Adapt the exact structure to the current code.

Requirements:

* Never navigate a DAP note to `response` unless that field actually exists.

* Validate `targetFieldId` against the active format before rendering the navigation action.

If the preferred field is unavailable:

1. Use an explicitly configured format-specific alternative, or
2. Show a tool-detail action instead.

Do not silently choose destinations through keyword matching.

# 6. Standardize Fallback Actions

Findings without a valid form destination should use a specific fallback action.

Examples:

* Review Clarity Details
* Review Consistency Details
* Review Medical Necessity Details
* Review Completeness Details

The finding must specify the fallback tool as structured metadata:

```ts
fallbackTool:
  | "clarity"
  | "consistency"
  | "medical-necessity"
  | "completeness";
```

Do not derive the fallback tool from the finding title.

Do not show a field-navigation action and fallback action simultaneously unless both provide distinct value.
