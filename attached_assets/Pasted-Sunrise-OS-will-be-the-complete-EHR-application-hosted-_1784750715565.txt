AI CLINICAL DOCUMENTATION ASSISTANT

Create an AI documentation assistant that can help authorized clinical users draft notes using structured information entered by the clinician.

The AI assistant must support:

- DAP notes
- SOAP notes
- BIRP notes
- GIRP notes
- Individual counseling notes
- Group counseling notes
- Case management notes
- Treatment-plan reviews
- Continued-stay reviews
- Discharge summaries
- Risk-assessment summaries
- ASAM dimension summaries
- Authorization-support narratives

The clinician should be able to enter:

- Service date
- Start and end time
- Location or delivery method
- Level of care
- Type of service
- Participants
- Presenting issue
- Interventions used
- Client response
- Progress toward goals
- Barriers
- Risk factors
- Protective factors
- Clinical observations
- Homework or next steps
- Follow-up plan

The AI should then create a draft note based only on the information provided.

AI SAFETY RULES

The AI must:

1. Clearly label all generated content as “AI Draft — Clinician Review Required.”
2. Never automatically sign or finalize a note.
3. Never invent symptoms, quotes, diagnoses, interventions, attendance, risk factors, medications, or clinical observations.
4. Never add information that the clinician did not provide.
5. Identify missing required information instead of guessing.
6. Flag contradictory information.
7. Highlight unsupported conclusions.
8. Require the clinician to review and edit every draft.
9. Require electronic signature before finalization.
10. Record who generated, edited, approved, and signed the note.
11. Preserve the original AI draft and all later revisions in the audit history.
12. Never allow AI-generated content to overwrite an existing signed note.
13. Never make treatment decisions independently.
14. Never replace clinical judgment.
15. Never produce stigmatizing or judgmental language.
16. Use person-first, objective, clinically appropriate language.
17. Avoid copying identical language across multiple client notes.
18. Warn users when a note appears too similar to another note.
19. Prevent documentation from being created for a client the user is not authorized to access.
20. Never send protected health information to an AI service unless the service, contract, configuration, and data-processing arrangement have been approved for PHI.

AI NOTE WORKFLOW

Create this workflow:

1. Clinician opens the correct client record.
2. Clinician selects the note type.
3. The system loads the client’s active treatment-plan goals.
4. Clinician selects the goal or objective addressed.
5. Clinician enters structured session information.
6. Clinician clicks “Generate Draft.”
7. AI creates a draft using only the entered information.
8. The system highlights missing fields and possible inconsistencies.
9. Clinician edits the draft.
10. Clinician confirms the note is accurate.
11. Clinician signs the note.
12. The system locks the signed version.
13. Any later correction must use an amendment process.
14. The full process must be recorded in the audit log.

GROUP NOTE WORKFLOW

For group documentation:

- Create one master group-session record
- Record topic, curriculum, interventions, start time, end time, facilitator, and attendance
- Create a separate individualized note for each participant
- Require individualized client response, participation, progress, and plan
- Do not create identical individualized notes
- Do not assume every participant had the same response
- Allow the clinician to review and edit each participant’s note separately
- Require individual approval before signing each client note

TREATMENT-PLAN CONNECTION

Every clinical note should allow the user to connect the service to:

- Active problem
- Treatment goal
- Measurable objective
- Intervention
- Progress status
- Continued need for treatment

Progress options should include:

- No progress
- Minimal progress
- Moderate progress
- Significant progress
- Goal achieved
- Regression
- Unable to assess

Require a brief explanation supporting the selected progress status.

CLINICAL LANGUAGE REQUIREMENTS

Use:

- Objective observations
- Behavioral descriptions
- Direct client statements only when actually entered
- Clear interventions
- Measurable progress
- Medical-necessity support
- A clear plan for continued treatment

Avoid:

- Unsupported diagnosis
- Vague statements
- Judgmental language
- Repetitive boilerplate
- Claims that were not documented
- Identical notes for different clients
- Statements written only to justify billing

DEVELOPMENT PROCESS

Before modifying the system:

1. Review the existing project.
2. List the current frontend framework.
3. List the current backend framework.
4. List the database and authentication system.
5. Identify all existing modules.
6. Identify what is complete, incomplete, or broken.
7. Create a checkpoint or backup.
8. Present a phased implementation plan.
9. Do not rebuild working modules unnecessarily.
10. Do not make destructive database changes without approval.
11. Build and test one module at a time.
12. Provide a plain-language testing checklist after each phase.

Start by creating the architecture assessment and implementation plan. Do not begin destructive changes until the plan is displayed.
