Complete one refinement task on the existing improvement branch:

**Task: Make Improve Clarity section-aware and add field-specific clarity navigation**

Do not begin permissions work, audit persistence, scoring changes, additional AI modules, medical-necessity changes, or unrelated UI work during this task.

Do not merge into `main`.

## Current problem

The existing `improveClarity()` workflow combines all Progress Note sections into one text string.

As a result:

* Clarity findings cannot identify which note section contains an issue.
* Clinical Documentation Review clarity findings use only `fallbackTool: "clarity"`.
* The clinician must manually determine where the suggested change belongs.
* Accepting a combined revision requires splitting the combined text back into fields, which can become unreliable when note sections contain paragraph breaks.

## Objective

Refactor Improve Clarity so it processes each Progress Note section independently.

Every clarity result must preserve:

* Note format
* Field identity
* Original field text
* Suggested field text
* Change descriptions
* Structured destination metadata

The clinician should be able to:

* Review clarity findings by section
* Jump directly to the affected field
* Accept changes for one section
* Accept all approved section changes
* Keep any original section unchanged

Do not automatically overwrite the legal note.

* Do not fabricate a change when no improvement is needed.

# 2. Process Each Note Section Independently

Refactor `improveClarity()` so it receives structured note sections.

Preferred input:

```ts
interface ClaritySectionInput {
  fieldId: ProgressNoteFieldId;
  fieldLabel: string;
  text: string;
```

Example:

```ts

    fieldLabel: "Behavior",

    fieldId: "intervention",
```

The exact sections must depend on the active note format:

* Response
* Plan

## DAP

* Data
* Assessment
* Plan

## SOAP

* Subjective
* Objective
* Assessment
* Plan

## GIRP

* Goal
* Intervention
* Response
* Plan

Do not send a field that does not exist in the selected note format.

# 5. Remove Proportional Text Re-Splitting

Remove the current behavior that:

1. Joins all note fields with paragraph separators.
2. Improves the combined text.
3. Splits the combined revision back across fields.

This proportional or paragraph-based re-splitting must no longer be used.

Each suggested revision must already belong to one known field.

Accepting a section revision should call a field-specific update such as:

```ts
onAcceptClaritySection(fieldId, suggestedText)
```

or an equivalent typed handler.

Accepting all revisions should pass a structured field update map.

Example:

```ts
{
  behavior: "...",
  intervention: "...",
  response: "..."
}
```

Do not update fields that have no accepted revision.

# 6. Add Field-Specific Clarity Findings to the Clinical Review

When the unified Clinical Documentation Review detects clarity improvements, create one finding per affected section or one grouped finding with structured child sections.

Preferred behavior:

* One finding for each affected field when the change is meaningful.
* Group trivial changes when necessary to avoid excessive noise.

Example:

```ts
{
  id: "clarity:intervention",
  priority: "suggested",
  category: "clarity",
  title: "Intervention wording could be clearer",
  explanation:
    "The intervention section contains wording that may be simplified without changing clinical meaning.",
  recommendedAction: "Review Intervention Wording",
  targetFieldId: "intervention",
  fallbackTool: "clarity",
  sourceFields: ["Intervention"]
}
```

Requirements:

* Use stable IDs:

  * `clarity:behavior`
  * `clarity:intervention`
  * `clarity:response`
  * `clarity:plan`
* Do not use text parsing to determine the target.
* Do not classify grammar or style issues as Critical.
* Most clarity findings should be:

  * Suggested Improvement
  * Informational
* Use Important only if unclear wording creates a meaningful documentation ambiguity.
* A finding with a valid field target should offer direct field navigation.
* Detailed clarity results must remain available through the individual Clarity tool.

# 8. Detect Stale Clarity Results

Store a lightweight source snapshot or hash for each reviewed section.

When the clinician attempts to accept a suggestion:

* Compare the current field text with the text reviewed by Improve Clarity.
* If unchanged:

  * Allow normal acceptance.
* If changed:

  * Show a stale-result warning.

Suggested message:

**This section has changed since the clarity review was generated. Review the current and suggested text before replacing it.**

Do not include patient text in general console logs.

Do not use a cryptographic dependency unless already available; a direct text comparison is acceptable.
